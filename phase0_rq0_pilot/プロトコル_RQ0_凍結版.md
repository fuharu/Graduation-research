# RQ0パイロット・プロトコル（凍結版 v1.1 / 2026-07-02）

tags: #決定 #実験
**凍結宣言**：本文書は elicit 実行前に確定する。実行開始後の変更は§8の履歴に理由付きで追記し、変更前のデータは破棄せず区別して報告する。

## 1. 目的
台帳生成（elicit）が、人間（タスク作成者）が重要とみなす前提をどの程度列挙できるか（カバレッジ）を最小コストで測り、機構全体への投資可否を判断する。

## 2. 実験構成
- タスク：3件（データ処理／API連携／小CLI。`tasks/task01〜03.json`）
- プロンプト：3変種（zero-shot／few-shot／批判的自問。`prompts/`）
- モデル：2種（AWS Bedrock経由：Claude Haiku系×1、Nova系×1。実行時に使用したmodelIdを記録）
- 反復：各セル3回、temperature=0.4
- 総呼び出し：3×3×2×3＝54

## 3. ゴールド前提の作成手順（elicit実行前に完了させる）
0. **前段（Phase 0a・分岐分析）**：同一タスクを同一モデルに5〜10回コード生成させ、サンプル間で実装が分岐する箇所（＝モデルが暗黙前提で埋めた箇所）を抽出・分類し、暗黙前提の類型を得る。**注意：ここで生成させるのはコードであり前提の列挙ではない**（elicitプロンプトとは独立の証拠。ゴールドがelicit出力と相関する汚染は生じない）。
1. タスク記述を確定してから、作成者（haru）が各タスクの前提を列挙する（5〜10個）。**Phase 0aの類型をチェックリストとして体系的に導出**し、類型外の前提も自由に追加する。
2. 各前提に付与：`id`／`statement`（検証可能な形で1文）／`type`（spec / api_contract / input / intent）／`importance`（critical / minor）。
3. **criticalの定義**：その前提が偽なら最終成果物が誤りになる、または大幅な手戻りが生じるもの。
4. 可能なら第2判定者（友人・先輩）に独立でレビューしてもらい、追加・削除の合意を記録。無理なら単独作成と明記。
5. ゴールド確定後は変更しない（漏れに気づいた場合は§8に追記し、感度分析として両方報告）。

## 4. 一致（マッチング）判定基準
elicitされた前提がゴールドと「一致」するとは：
- **判定テスト**：「その前提が崩れたとき、同じ失敗（同じ成果物の誤り）につながるか」— YESなら一致。
- 言い換え・粒度違いは一致とみなす（例：「ageは整数」と「ageフィールドは年単位の整数値」）。
- 1つのelicit前提が複数ゴールドを包含する場合、包含される全ゴールドを covered とする。
- 複数のelicit前提が1つのゴールドを分担する場合、合わせて崩壊条件を覆っていれば covered。
- ゴールドに対応しないelicit前提は誤りではなく「余剰」（適合率の分母に入る）。ただし**明らかに誤った前提**（タスク記述と矛盾）は `wrong` とフラグし別集計。
- 判定はシート上で行い、迷った事例は `note` 列に理由を書く（全件公開前提）。

## 5. 指標
- **主要**：critical前提の再現率（タスクごと→タスク横断はブートストラップCI）
- 副次：全前提の再現率／適合率／wrong率／反復間の安定性（3回中何回列挙されたか）
- プロンプト変種・モデル間の比較は探索的（多重補正なし、CIで報告）

## 6. 分岐基準（事前固定）
| critical再現率（最良プロンプト×モデルの中央値） | 判断 |
|---|---|
| ≥ 70% | 続行。最良変種をPhase 1の正式elicitに採用 |
| 50〜70% | ハイブリッド化：人手シード前提＋LLM補完を機構の正式仕様に変更（企画書改訂） |
| < 50% | 台帳は人間が与える設計に変更し、研究の重心をモニタ＋設計回帰へ。指導教員と再相談 |

いずれの場合もRQ0の結果自体は論文の知見として報告する（ネガティブでも価値がある）。

  (c) 上記ツールが検出できない観点（リスト・集合リテラル、数値リテラル、if/elseの条件、
