# 分岐の注釈ガイド

## 記録する / しない の判定

判定テスト1（代替案テスト）:
  そのタスク記述を満たしつつ、振る舞いが変わる代替案を1つ以上挙げられるか。
  挙げられないなら前提ではない。

判定テスト2（出力テスト）:
  この違いによって、同じ入力に対する出力や副作用が変わるか。
  変わらないなら実装の書き方の差であり、前提ではない。

記録しないもの:
  - 変数名・関数名・コメント・内包表記かループかの差
  - 同じ結果を別の書き方で得ているだけの差
  - 8/8 で一致している項目（ただし下記の例外あり）

例外: 8/8 で一致していても、タスク記述が指定しておらず、
全サンプルが同じ暗黙前提を置いていると判断できる場合は記録する。
その際 n_samples_affected に「8/8（分岐なし・人手追加）」と書いて区別する。
（根拠: 分岐分析は「モデルが迷った前提」しか検出できない。
 モデルが単一の解釈に収束する現象は semantic collapse として報告されている）

## assumption_statement の書き方

- 1文で、検証可能な形で、タスクについての主張として書く
- ×「欠損の扱い」（名詞句。真偽が定まらない）
- ×「r.get() を使うべき」（コードの話であって前提ではない）
- ○「全レコードに age フィールドが存在する」

## monitorable の判定

実行時の観測と突き合わせて真偽を判定できるなら yes。

yes の例: 「CSVにヘッダ行がある」「ファイルはUTF-8で読める」
         「APIレスポンスはJSON配列である」
no  の例: 「該当なしのとき空リストを返す」「最初の1件だけ返す」
         「O(n)のハッシュマップを使う」

no は設計上の選択であり、観測しても矛盾が生じない。
機構の監視対象外だが、台帳には載せるため記録はする。

## importance の判定

critical: その前提が偽なら最終成果物が誤りになる、または大幅な手戻りが生じる
minor: それ以外

判定はタスク記述と成果物の用途に依存する。
迷った場合は note に理由を書く。

## note 列

判断の理由を残す。半年後の自分と、第2判定者が判断を追えるように。
